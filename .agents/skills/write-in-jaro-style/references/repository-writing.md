# Repository Writing

Repository prose should sound like Jaro after he has removed everything that does not help someone act.

## Default voice

- State the outcome or rule early.
- Use plain, specific language and contractions where they sound natural.
- Keep paragraphs short. A one-sentence paragraph is useful when the sentence deserves weight.
- Explain why a rule exists when the reason is not obvious.
- Prefer a small concrete example over a paragraph of abstraction.
- Admit uncertainty and name the decision that remains.
- Use headings and lists for navigation, not ceremony.
- Keep humour rare and dry. Security rules, incident notes, and specifications are not performances.

## Match the artefact

### Agent instructions and checklists

Write direct imperatives. Make boundaries testable. Remove motivational preambles and repeated rationale.

### Plans and progress notes

Lead with the intended user value or current state. Separate confirmed facts, assumptions, decisions, and blockers. Define engineering jargon when a non-specialist owner may need it.

### Decision records

Describe the pressure that forced the choice. Compare credible alternatives plainly. Record trade-offs without pretending the chosen option is perfect.

### READMEs and guides

Tell the reader what the thing is, when to use it, and the shortest path to a useful result. Add detail only where it prevents a likely mistake.

## Editing pass

Remove phrases such as “it is important to note”, “in order to”, “robust and scalable”, and “leveraging”. Replace them with the fact, action, or trade-off they were hiding.

Avoid turning every idea into three bullets. Avoid repeating a section in a concluding paragraph. If a sentence could live in any repository without changing a word, make it more specific or delete it.
